# 复现评测

[返回项目首页](../README.zh-CN.md)

[新增实验协议](extended-evaluation-protocol.zh-CN.md)涵盖 Gemma，以及独立的 12 条开发用例、36 条测试用例扩展集。已完成的三模型、四方法同页面比较见[扩展结果](extended-results.zh-CN.md)：直接评分准确率为 Gemma 31/36、Qwen 30/36、GLM 21/36，错误 enum 动作分别为 1/30、1/30 和 8/30。布尔回答单独报告。Gemma 的扩展缓存阶段已完成全部 108 次决策和 72 次缓存／全新计算比较；所有比较通过，三个条件均保持 31/36 正确、一次错误 enum 动作。新增实验计划中的 1,096 次测量已全部完成。单独的 [Gemma 原始测试集结果](gemma4-results.zh-CN.md)为 26/28 正确，其中包含一次筛选后首项选择错误（26 条 enum 请求中的 1 条）。最新[核心检查](../benchmarks/results/extended-release-checks/core-tests.json)通过 161 项测试，无失败或错误（pytest 3.76 秒；JUnit 测试集时间 3.752 秒）。

公开测试数据均为专门为本仓库编写的虚构场景，不含生产导出、录音、截图、对话记录或由私人示例改写的内容。16 条开发用例与 28 条冻结测试用例使用不同的话语和 ID。`benchmarks/fixtures/manifest.json` 记录精确的 SHA-256 哈希；运行器会拒绝发生变化的数据。小规模公开数据集适合回归检查，但不能证明普遍准确性或安全性。

默认 margin 阈值为 **0.0**，在测试推理前固定。不得使用测试标签调整提示词、阈值、模型选择规则或缓存容差，再将其描述为未受调参影响的测试结果。开发实验必须先于测试运行。后续调参需要新的留出集和新的清单。仓库中的测试区分模型决策与执行保护。

## 运行完整比较

安装开发和 MLX 依赖后，在源码检出目录中执行以下命令。将 `MODEL` 设为已有的本地 MLX 模型目录。运行器不会下载权重或修改共享模型目录。

```sh
export MODEL=/path/to/local/mlx-model
python -m benchmarks.run --model "$MODEL" --split dev --output results/dev-v1
python -m benchmarks.run --model "$MODEL" --split test --repeats 3 \
  --output results/test-v1 --parity
python -m benchmarks.cold_start --model "$MODEL" --repeats 3 \
  --output results/process-cold-v1
```

每次运行使用新的输出目录；不得覆盖之前的尝试。`--limit 4` 会生成明确标注的冒烟测试子集。`--modes direct code json` 和 `--conditions kv_cold same_page_new_utterance page_update` 用于选择方法与条件；`--cohorts` 是 `--conditions` 的别名。默认包含上述三种方法和三种条件。重复一次的完整测试会执行 252 次计入统计的决策，以及另行记录的准备调用。一次只运行一个模型，以免 Metal 工作负载相互竞争。解释结果时应记录其他正在运行的应用；运行器不会停止它们。准确率统计包含全部尝试，保留模型错误和无效输出。JSON 输出可能较大，因为每次试验都保留证据。

扩展集使用独立的冻结清单；运行器和证据审计都需传入 `--fixtures-dir benchmarks/fixtures/extended-v1`。已完成的主要比较先运行独立的 12 条开发用例，再明确使用 `--modes direct code json json_code --conditions same_page_new_utterance`。每个模型因此产生 144 条测试记录，但只有 36 条不同的质量用例。精确命令与单独的 Gemma 直接评分缓存阶段见[新增实验协议](extended-evaluation-protocol.zh-CN.md)。不能从主要的热缓存比较推断每个扩展模型都覆盖三种缓存条件或新进程条件，也不能将其与原始数据集混合。

## 比较内容

| 方法 | 输出 | 计算方式 |
|---|---|---|
| `direct` | 一个经 tokenizer 验证的候选编码，映射为业务 ID | 官方模型前向计算，将最后位置的 logits 限制在允许选项内，包括不匹配与弃权 |
| `code` | 单个选项编码 | 相同模型、相同语义／编码提示词，使用官方无约束贪心生成，`max_tokens=1` |
| `json` | `{"candidate_id":"..."}` | 相同模型与语义状态／策略，使用无约束贪心 JSON 生成，上限 96 个 token |
| `json_code`（补充方法，需显式启用） | `{"choice":"<option code>"}` | 相同语义状态／策略／选项，无约束贪心 JSON 生成，上限 96 个 token，随后精确映射编码到 ID |

直接评分方法限制词表，这是明确的建模差异。单编码基线可能输出非候选 token；这属于格式失败，不会被悄悄强制映射为最接近的候选。JSON 必须能够解析，且只包含预期的键以及当前允许的 ID。两种基线都不使用生成输出语法约束。即使 `max_tokens=1`，MLX-LM 也可能安排前瞻计算；计时包含实际完成的工作。JSON 方法是普通自回归生成。任何方法的输出分数都不是校准后的正确概率。

补充的 `json_code` 对照是在原始 Qwen 测试暴露 JSON 输出混淆选项编码和业务 ID **之后**加入的。它是公开说明的后续比较，不属于原始预先登记的三方法运行，也不是未受结果影响的盲测。目的在于避免因不必要地增加输出格式难度而宣称质量优势。只有要求的输出格式及其解析器不同；语义策略、状态、选项、拒绝阈值，以及原始 `code`／`json` 提示词均保持不变。原始 JSON 失败仍保留在原始 252 次试验报告中。JSON-code 生成仍然是自回归；格式错误的对象或未知编码仍计为格式失败。没有语法约束强制其给出有效结果。

先运行开发示例，再运行未改动的冻结测试，并保留两者输出：

```sh
python -m benchmarks.run --model "$MODEL" --split dev --modes json_code \
  --output results/json-code-dev-v1
python -m benchmarks.run --model "$MODEL" --split test --modes json_code \
  --output results/json-code-test-v1
```

默认仍选择原始三种方法。显式传入 `--modes direct code json json_code` 会包含全部四种方法，每次完整测试重复产生 336 次计入统计的决策；仅使用 `--modes json_code` 则产生 84 次。运行元数据会标注此补充对照并记录其来源。

所有方法接收相同的测试状态、候选语义、问题和话语。提示词格式只按所需输出格式作必要差异。方法／条件／用例顺序使用固定种子打乱。直接评分引擎的 margin 阈值与基线生成配置均被记录。重复运行复用相同输入，因此衡量的是耗时变化，而非新增独立质量样本。不得用重复次数夸大测试集规模。

| 条件 | 准备步骤与计时工作 |
|---|---|
| `kv_cold` | 权重已加载；决策绕过所有提示词快照 |
| `same_page_new_utterance` | 用一条单独记录的请求预热同一页面；计时请求使用不同话语并重新计算其后缀 |
| `page_update` | 用一条已记录的请求预热另一个较早页面／版本；计时请求在相同缓存命名空间中使用当前状态和已变化的候选 |
| `process_cold_start` | 每次尝试启动独立 Python 进程，加载权重并运行第一条用例；包含解释器启动、模型加载、推理和退出 |

进程条件有意不清空操作系统文件系统缓存。不得将其称为机器启动或冷磁盘测量。它只使用第一条用例，并明确报告这一范围。权重已加载的条件单独记录加载时间。快照准备延迟不计入决策计时间隔，但保留完整结果与耗时，使预热成本可见。不缓存最终答案。缓存命中只指 token 前缀计算的复用。

## 指标与产物

`trials.jsonl` 记录每次完成的尝试、标准答案、原始预测、可用时的分数、墙钟耗时、缓存信息、输入规模、内存以及所有异常。无效输出保留原始文本。准备失败会作为明确的失败保留，不会悄悄替换成成功的全新决策。`summary.json` 在每次试验后更新，并标注未完成运行。`metadata.json` 包含数据哈希、模型名称、运行配置、依赖版本、硬件、源码提交／工作区修改状态，以及提示词、后端、契约、引擎和基准实现的 SHA-256 哈希。后端输出保留模型配置与 tokenizer 哈希、量化设置和运行时身份。模型绝对路径及用户主目录均被隐去。

各指标使用以下分母：

- **准确率：** 状态与预期完全一致，若为选择结果则业务 ID 也必须正确，除以全部尝试。`no_match` 与 `abstain` 是不同标签。
- **返回选择错误率：** 错误返回的选择数，除以所报告分组中的全部尝试。旧字段名为 `false_action`，但全类型分组同时包含布尔回答和动作。应以 enum 请求数为分母报告 enum 动作错误，并单独报告布尔分类错误。宿主应用拦截动作，不会使模型预测变成正确。
- **原始选择准确率／原始选择错误率：** 使用分数 margin 弃权策略之前的 `raw_selected_id`，以相同报告分组中的全部尝试为分母。旧聚合字段 `raw_false_action` 同样混合不同类型。保留 ID 映射为各自不同的 `no_match`／`abstain` 状态。错误原始动作随后被策略弃权，仍是原始错误及原始错误动作；正确原始动作随后被弃权，则原始选择正确，但返回动作不正确。无效生成输出、缺失原始选择和异常计为原始选择错误，不计为原始动作选择。这些字段将模型首选质量与 margin 拒绝、执行器保护分别呈现。
- **拒绝率：** 有效的 `no_match` 或 `abstain` 输出数除以全部尝试。弃权也单独报告。
- **Enum 可执行请求覆盖率：** 正确动作选择数除以标签中存在可执行动作的 enum 请求数。错误选择不计入覆盖。旧的全类型 `executable_request_coverage` 则包含所有预期为 `selected` 的回答，包括布尔事实；应将其标为混合类型的正确选择覆盖率。
- **格式有效率：** 有效的允许 ID 或保留拒绝结果数除以全部尝试。异常与无效生成输出均不满足此指标。
- **延迟：** 使用线性插值计算 p50、p95，按方法和条件分组。成功调用的耗时包含语义错误／格式无效的输出。失败调用单独报告延迟分布和数量。质量指标始终包含失败。分组规模小时，百分位数仅作描述。
- **内存：** 进程生命周期内的峰值 RSS，以及可用的 MLX 活跃、峰值和缓存内存。进程中的峰值是累计观测，不是独立的单次调用内存分配；不得把 RSS 和 MLX 内存当作独立内存池相加。

原始 28 条测试包含 16 条可执行 enum 请求、10 条 enum 拒绝请求，以及 2 条选中布尔回答：旧的选择分母为 18，而不是 18 个应用动作。扩展集有 15 条可执行 enum 请求、4 条选中布尔回答，混合分母为 19。更正后的纯动作解释见[按类型拆分的历史结果推导](../benchmarks/results/legacy-kind-breakdown.json)；它不修改原始试验记录。

早期运行汇总保持不可变。要从其已记录试验计算新增原始选择字段，而不重新推理或覆盖证据：

```sh
python -m benchmarks.recompute results/test-v1 --output results/test-v1-derived.json
```

派生报告记录源试验与指标代码的 SHA-256 哈希，以及原始完成状态。报告代码也可直接调用 `benchmarks.metrics.summarize(rows)` 或 `grouped_summary(rows)`。现有基于状态的指标保留原始定义；派生报告在其旁边增加原始选择指标。

发布前，将审核后的副本与原始运行比较，并在不加载模型的情况下验证运行安排、冻结标签、指标总量、保留的无效输出及实际前缀复用：

```sh
python -m benchmarks.audit runs/example --public benchmarks/results/example \
  --source-revision '<recorded-source-commit>'
```

运行未完成、证据副本有差异、派生总量不正确、准备成本缺失，或声明的缓存条件没有预期复用时，审计会以失败状态退出。已记录的模型错误仍是有效证据，会计入报告。派生指标报告会对照源试验哈希验证，不会被误当作原始输出的不可变副本。

后端在返回前同步实际 MLX 计算。外层墙钟时间包含请求／结果组织工作。进程冷启动墙钟时间由父进程测量。保留模型加载失败与子进程超时。绝不以猜测的决策替换异常。

`--parity` 写入 `parity.jsonl`，将完整全新计算的候选 logits 与同页面缓存路径、页面更新后路径分别比较。默认原始 logits 绝对容差为 0.5、相对容差为 0.0，受限 softmax 分数最大差为 0.1，并要求获胜编码相同。这些默认值与可选实机模型测试一致，且在冻结测试推理前已设定。每条记录包含容差、最大绝对差／分数差、双方分数，以及获胜编码是否一致。任何不匹配或异常都会使命令以非零状态退出；`summary.json` 记录一致性通过／失败数，在所需一致性阶段完成前，运行始终标为未完成。

同时报告数值一致性和决策一致性。数值接近的并列结果仍可能改变选中动作。这项检查不能证明每种模型／缓存架构都正确。确定性的过期结果执行测试与模型语义准确率分开统计。

## 解读发布结果

应一并公开完整冻结数据集、所有方法与条件、失败、命令、硬件、依赖与模型身份。在明确说明的质量水平下，与实测最强基线比较。单个较小的热前缀耗时不足以证明整体优势。应说明是否真正证明速度或质量优势；负面结果同样是结果。分别呈现各模型测量，并区分实际推理支持与仅在磁盘上发现的权重。浏览器演示分别展示选中动作、执行回执以及 DOM／状态结果；执行器保护不能代替模型质量评估。
